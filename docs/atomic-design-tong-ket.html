Tổng kết: Atomic Design trong Next.js

Tài liệu tóm tắt dành cho Backend Developer học frontend. Ví dụ thực tế lấy từ repo atomic-design-project-template (Next.js 16.4, React 19, Tailwind, TypeScript).

[Brad Frost] nguyên lý gốc [React thực tế] cách cộng đồng áp dụng [Quy tắc Next.js] framework bắt buộc [Ý kiến] lựa chọn có tranh luận

1. Tư duy Atomic Design

Vì sao ra đời

[Brad Frost] Năm 2013, responsive web khiến cách làm "thiết kế từng trang" bị vỡ: cùng một nút nhưng mỗi trang một kiểu, sửa header phải sửa N chỗ. Ý tưởng cốt lõi:

"We're not designing pages, we're designing systems of components." (Stephen Hay, được Brad Frost trích dẫn)

Ông mượn ẩn dụ hóa học: nguyên tử ghép thành phân tử, phân tử tạo thành sinh vật. UI đi từ nhỏ đến lớn, từ trừu tượng đến cụ thể. 

Atoms ──► Molecules ──► Organisms ──► Templates ──► Pages

Ba điểm hay bị hiểu sai

  • Atomic Design là mental model để xây design system, ban đầu không phải cấu trúc thư mục.
  • Atoms gốc gồm cả màu sắc và font chữ. Trong Tailwind, chúng trở thành design tokens (CSS variables), không phải component.
  • Đây không phải quy trình tuyến tính: bạn đi qua lại giữa tổng thể và chi tiết.

Sau khi tách: atom không biết domain

// components/atoms/Badge.tsx
const toneClass = {
  success: "bg-green-100 text-green-700",
  warning: "bg-yellow-100 text-yellow-700",
};

export function Badge({ tone, children }: { tone: keyof typeof toneClass; children: ReactNode }) {
  return <span className={`${toneClass[tone]} text-xs px-2 rounded-full`}>{children}</span>;
}

Data đi xuống (props), event đi lên (callback). State chỉ sống ở một nơi, giống single source of truth.

Liên hệ backend: giống và khác

Khái niệm Giống Khác (đừng đánh đồng)
Separation of Concerns Mỗi cấp có phạm vi rõ ràng Atomic chỉ tách cùng một loại (UI) theo kích thước. Nó không tách business logic khỏi UI.

Composition Ưu tiên composition hơn inheritance React lồng theo cây, có children và slot

3. Áp dụng vào Next.js

Mỗi thư mục trả lời một câu hỏi

app/          → "Có những URL nào?"            (routing, mỏng như controller)
components/   → "UI dùng chung trông thế nào?"  (Atomic, không biết domain)
features/x/   → "Nghiệp vụ X gồm những gì?"     (schema, service, action, UI riêng)
lib/          → hạ tầng chung

Hai cấu trúc

A. Atomic thuần B. Atomic + Feature
Ý tưởng Mọi component chia theo cấp Atomic chỉ cho components/, nghiệp vụ nằm trong features/
Ưu điểm Đơn giản, hợp với design system Sửa hoặc xóa một feature chỉ trong một thư mục
Nhược điểm Code của một nghiệp vụ rải ở 4 thư mục; organisms/ thành bãi rác Phải quyết định shared hay feature; cần luật import
Phù hợp App nhỏ, thư viện UI App vừa và lớn, nhiều người làm
Backend tương ứng Package-by-layer Package-by-feature

Shared hay feature?

Component có biết domain không?
├── Có    → features/<domain>/components/
└── Không → Đã dùng ở ≥ 2 nơi?
            ├── Có   → components/<cấp>/
            └── Chưa → để trong feature trước, chuyển lên khi có lần dùng thứ 2

Server Component và Client Component

Server (mặc định) Client ('use client')
Chạy ở Chỉ server Server render HTML, sau đó hydrate trong trình duyệt
async/await, secret Có Không (chỉ biến NEXT_PUBLIC_*)
State, effect, onClick Không Có

[Quy tắc Next.js] 'use client' là ranh giới: mọi thứ file đó import đều thành client. Atom không có hook thì không cần directive này, nhờ vậy dùng được ở cả hai phía.

Cần 'use client': hook có state hoặc effect, event handler là hàm JS, browser API. Không cần: render props, <Link>, <form action>, fetch dữ liệu.

Đặt 'use client' càng gần lá càng tốt. Server Component có thể được truyền vào Client Component qua children.

Lỗi thường gặp

Lỗi Nguyên nhân
Event handlers cannot be passed to Client Component props. Server Component truyền hàm onClick xuống
Functions cannot be passed directly to Client Components... Truyền hàm thường (ví dụ cell) qua ranh giới client
process.env.X là undefined ở trình duyệt Biến không có tiền tố NEXT_PUBLIC_ chỉ tồn tại trên server, đây là cố ý

Data, state, event: đặt ở đâu

Việc Vị trí
Đọc dữ liệu Service hoặc repository, được gọi từ page.tsx (server)
Ghi dữ liệu Server Action ('use server')
Search, filter, page URL (searchParams): chia sẻ được, nút Back hoạt động đúng, server đọc được
UI state useState trong client leaf
Business rules Backend
Global state lib Chưa cần, cho đến khi có nhu cầu thật

Mẫu Server Action

export async function createTaskAction(input: unknown): Promise<ActionResult> {
  try {
    await requireSession(TASK_WRITE_PERMISSION)          // 1. kiểm tra quyền
    const parsed = taskFormSchema.safeParse(input)        // 2. validate lại, không tin client
    if (!parsed.success) return validationFailure(parsed.error)
    await taskRepository.create(parsed.data)              // 3. gọi repository
  } catch (error) {
    return toActionFailure(error)                         // 4. thông báo an toàn cho người dùng
  }
  revalidateTaskPages()                                   // 5. render lại /tasks, /dashboard
  return { ok: true }
}

Hàm trả về ActionResult thay vì throw, vì ở production lỗi bị throw ra sẽ bị Next.js thay bằng thông báo chung chung.

Luồng dữ liệu

ĐỌC  Browser GET /tasks?q=..&status=..
     → shell gửi ngay → TaskList: await searchParams → Zod → taskRepository.list
     → demo (bộ nhớ) | rest (backendRequest → GET {API_BASE_URL}/tasks, validate response)
     → stream TaskFilters + TaskTable + Pagination

GHI  TaskStatusSelect: setOptimisticStatus(next)  → UI đổi ngay
     → updateTaskStatusAction (POST) → requireSession → Zod → repository.update → PATCH
     → revalidatePath → ok: dữ liệu thật thay giá trị optimistic | lỗi: tự quay về giá trị cũ

Presentational và logic

Nhóm Ví dụ Chạy ở
Presentational, không biết domain Button, Badge, DataTable, Pagination, DashboardTemplate Server (trung lập)
Presentational, biết domain TaskTable, TaskPriorityBadge Server
Tương tác TaskFilters, TaskStatusSelect, DeleteTaskButton, TaskForm Client
Điều phối dữ liệu TaskList trong page.tsx Server
Logic, không có UI actions.ts, services/*, schemas.ts Server

Tích hợp REST API

  1. .env.local: API_MODE=rest, API_BASE_URL=.... File lib/env.ts validate khi khởi động và có server-only để chặn lộ secret.
  2. Contract nằm ở đầu rest-task-repository.ts. Backend khác contract thì chỉ sửa adapter này.
  3. Auth fail-closed: phải cài đặt resolveSession() trong lib/auth-provider.ts. Nếu chưa, mọi trang hiện "Sign-in required".
  4. Lỗi HTTP được chuyển thành ApiError có mã: NOT_FOUND, VALIDATION_ERROR, TIMEOUT, NETWORK_ERROR, INVALID_RESPONSE.

Chạy thử: cp .env.example .env.local && pnpm dev rồi mở /tasks. Xem riêng từng component bằng pnpm storybook.

5. Vấn đề thực tế

Molecule hay Organism?

1. Có biết domain không?        → Có: features/. Không cần phân loại (khoảng 80% trường hợp)
2. Có phải một VÙNG đứng riêng?  → Organism
3. Làm đúng MỘT việc?            → Molecule
4. Vẫn phân vân?                → Chọn cấp thấp hơn. Chuyển lên sau rất rẻ.

Số lượng atom bên trong không quyết định cấp. ConfirmationDialog chứa cả molecule nhưng vẫn là molecule. DataTable không chứa molecule nào nhưng là organism.

Câu trả lời ngắn

Câu hỏi Trả lời
Áp dụng Atomic cho mọi component? Không. Chỉ cho components/ dùng chung. Feature để phẳng.
Phải đủ 5 cấp? Không. Repo chỉ có 1 template; layout.tsx và page.tsx gánh phần còn lại.
Atomic thay thế Feature-based? Không. Hai trục khác nhau (kích thước UI và nghiệp vụ), dùng cùng nhau.
Composition hay component mới? Chỉ khác nội dung thì dùng composition (slot, render prop). Khác cấu trúc hoặc hành vi và lặp ≥ 2 lần thì tạo component.

Dấu hiệu over-engineering

  • Thư mục organisms/, templates/ rỗng "cho đủ bộ".
  • Bọc nhiều tầng: TaskButton → PrimaryButton → Button.
  • <Title> chỉ là <h2 className="...">.
  • Đưa lên shared trước lần dùng thứ hai, rồi phình ra 12 prop boolean.
  • Sửa chữ trên một nút mà phải mở 5 file. Tranh luận phân loại lâu hơn viết code.

Refactor dự án có sẵn (Strangler Fig)

  1. Khảo sát UI lặp lại nhiều nhất và lệch style nhiều nhất.
  2. Tạo khung thư mục cùng ESLint no-restricted-imports ngay từ đầu (giống ArchUnit).
  3. Gom design tokens.
  4. Tách atoms, thay dần ở những chỗ đang sửa. Không làm big-bang.
  5. Tách molecules khi thấy pattern lặp lại.
  6. Chuyển component có domain vào features/.
  7. Đẩy 'use client' xuống các lá.
  8. Code ổn định không ai sửa thì cứ để đó. Giữ E2E test làm lưới an toàn.

Anti-pattern bổ sung

Bảng đầy đủ nằm ở docs/component-guidelines.md mục 6. Thêm vào đó:

  • Phân loại theo kích thước nhìn thấy thay vì phạm vi trách nhiệm.
  • "Atomic chỉ ở tên thư mục": đổi tên thư mục nhưng không có quy tắc phụ thuộc.
  • Shared component có prop mang tên domain (tasks, onDeleteTask).
  • Template lặp lại layout.tsx; nhầm Atomic Template với file template.tsx của Next.js.
  • Tự viết lại phần tử native (<select>, <dialog>, <input type="date">).

Đính chính cho Next.js 16.4

  • error.tsx: từ Next 16.3 dùng prop retry (lấy lại dữ liệu rồi render lại) thay vì reset.
  • cacheComponents: true: đọc searchParams ngoài <Suspense> sẽ bị dev overlay cảnh báo blocking-route. Hãy tách component con async và bọc Suspense.
  • Data access: không gọi fetch(process.env...) trực tiếp trong component. Đi qua services/*-repository.ts và backendRequest.

Checklist khi tạo component mới

  1. Đã có component sẵn chưa? Ghép từ component có sẵn được không? Thẻ HTML native làm được không?
  2. Component có biết domain không? → features/ hay components/
  3. Có cần state, event handler hoặc browser API không? → có cần 'use client' không
  4. Dữ liệu đến từ đâu? → props, không gọi fetch trong component
  5. Chạy pnpm check && pnpm build để ESLint xác nhận ranh giới import.

Câu hỏi ôn tập

Thử tự trả lời trước, rồi mới mở gợi ý.

Phần 1: Tư duy

  1. Designer yêu cầu: "Mọi nút primary đổi sang màu indigo và rounded-lg." Đếm số chỗ phải sửa trước và sau khi refactor. Nếu có 10 trang thì sao?
    Gợi ý
    Trước: mỗi thẻ <button> có class riêng, số chỗ tăng theo số trang × số nút. Sau: chỉ sửa trong Button.tsx (bảng variant và class nền), luôn là 1 file dù có bao nhiêu trang.
  2. Nếu Badge nhận task: Task thay vì tone + children, điều gì hỏng khi trang Projects cần badge "Active/Archived"? Lỗi tương tự ở backend là gì?
    Gợi ý
    Badge bị gắn chặt vào type Task, không dùng lại được. Backend: một utility formatCurrency(order: Order) thay vì formatCurrency(amount), nên Invoice không gọi được.
  3. Đồng nghiệp ánh xạ: Atom = Entity, Molecule = Value Object, Organism = Service, Page = Controller. Phần nào có lý, phần nào sai?
    Gợi ý
    Có lý: phụ thuộc một chiều, ghép từ nhỏ đến lớn, Page hơi giống controller (điều phối). Sai: Entity và Value Object chứa quy tắc nghiệp vụ, còn atom cố tình không biết domain. Cả 5 cấp đều thuộc presentation layer, không phải domain hay service.

Phần 2: Năm cấp độ

  1. Phân loại: Avatar, UserMenu (Avatar + tên + dropdown 3 link), Pagination, LoginForm.
    Gợi ý
    • Avatar: atom.
    • UserMenu: molecule nếu chỉ làm một việc (menu người dùng); organism nếu thành một vùng lớn.
    • Pagination: molecule (repo đặt ở molecules/).
    • LoginForm: biết nghiệp vụ auth, nên đặt trong features/auth/. Câu hỏi về cấp gần như không còn quan trọng.
  2. ProductCard cần nút "Thêm vào giỏ" gọi POST /cart. Đặt lời gọi API ở đâu? ProductCard nhận thêm gì?
    Gợi ý
    Lời gọi API đặt trong Server Action (features/products/actions.ts), validate input và kiểm tra quyền. ProductCard chứa <form action={addToCart}> với hidden productId. Chỉ khi cần trạng thái "Đang thêm..." mới tách một client leaf dùng useFormStatus. Nhớ lại onDelete ở Phần 1: data đi xuống, event đi lên.
  3. Vì sao CatalogTemplate nhận title + children thay vì products: Product[]?
    Gợi ý
    Template chỉ biết slot, không biết domain. Nếu nhận products, trang /orders không dùng lại được và template phải import type Product.

Phần 3: Next.js

  1. Theo cấu trúc B, đặt các component sau ở đâu: DatePicker (dùng ở orders và tasks), OrderStatusBadge, CheckoutForm, ProductFilters (chỉ dùng ở /products)?
    Gợi ý
    DatePicker: trước hết thử <input type="date">; nếu vẫn cần component riêng thì đặt ở components/molecules. OrderStatusBadge và CheckoutForm: features/orders. ProductFilters: features/products/components (hoặc app/products/_components nếu gắn chặt với một route).
  2. Cái nào cần 'use client': (a) ProductList render mảng; (b) Tabs; (c) SearchField dùng <form action="/products">; (d) ProductCard có onClick gọi console.log; (e) đồng hồ đếm ngược?
    Gợi ý
    Cần: (b), (d), (e), vì có state, event handler là hàm JS, hoặc timer. Không cần: (a), (c), vì chỉ render, và form GET là hành vi native của trình duyệt.
  3. Đồng nghiệp thêm 'use client' vào page.tsx để dùng useState cho ô tìm kiếm. Nêu ít nhất 2 hậu quả và cách sửa.
    Gợi ý
    Hậu quả: page không còn async fetch trên server được; cả cây component bị đẩy vào bundle client; không đọc được secret env. Cách sửa: đưa keyword lên URL, tách ô tìm kiếm thành client leaf giống TaskFilters, page vẫn là server.

Phần 4: Ứng dụng Task

  1. Thêm bộ lọc theo priority trên /tasks. Liệt kê file cần sửa theo thứ tự. Có file nào trong components/ phải sửa không?
    Gợi ý
    Thứ tự: schemas.ts (thêm priority vào taskListQuerySchema; type tự cập nhật theo) → services/demo-… và rest-… (lọc theo priority) → page.tsx (đọc raw.priority, cập nhật hrefForPage) → task-filters.tsx (thêm Select và URL param). TASK_PRIORITY_OPTIONS đã có sẵn. Không sửa gì trong components/, vì atom Select đã đủ.
  2. Đồng nghiệp muốn thêm 'use client' vào DataTable để sắp xếp cột. Điều gì hỏng ngay? Đề xuất cách khác.
    Gợi ý
    Hàm cell từ TaskTable (server) không serialize được qua ranh giới client, dẫn đến lỗi "Functions cannot be passed directly to Client Components". Cách khác: sắp xếp qua URL (?sort=title) để server sắp xếp, hoặc chỉ biến nút ở header cột thành client leaf.
  3. createTaskAction nhận input: unknown và validate lại dù TaskForm đã validate. Vì sao không bỏ bớt một lần?
    Gợi ý
    Validate ở client là để cải thiện UX. Validate ở server là để bảo mật, vì Server Action là POST endpoint công khai, ai cũng gọi được. Backend tương tự: bỏ @Valid ở controller vì "frontend đã kiểm tra rồi".
